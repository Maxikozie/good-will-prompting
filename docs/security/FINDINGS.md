# Security findings

## Review basis and severity

Source review on 2026-09-30, baseline **`ffdddc0`**, after pulling main and reading the [threat model scope](THREAT_MODEL.md). References below are repository-relative `file:line` locations at that commit. No fixes, new tests, application execution, destructive probes, external-model calls or Aikido scan were performed. Reproduction descriptions are code-path reasoning, not claims of executed exploits. The LLM changes initially seen as team work were committed and pushed to main during review and are included in this baseline.

Severity considers the actual exposure: localhost/mock fixtures today, with no assumed public deployment. **critical** means demonstrated broad catastrophic exposure; **high** means a reachable confidentiality/verification-authority failure; **medium** means a constrained integrity/privacy/availability failure or a concrete internal primitive that must be corrected before integration; **low** means limited-impact hardening. No critical issue was established. Internal Brain functions are not currently remotely callable; their defects are identified as such.

The table records the **pre-fix baseline**. The subsequent [MCP authorization change](MCP_AUTH.md) addresses the MCP portion of F01, gates legacy MCP access for F02, corrects F07 tool annotations, and adds the Brain tool authorization boundary relevant to F14. HTTP exposure and repository-level findings remain open; this is not a claim that all findings are resolved. Each fix plan includes a regression test; none authorizes weakening existing checks. The table contains **18 findings: 2 high, 13 medium, 3 low**.

## Important limits and non-findings

- SQL values in the reviewed repositories are parameter-bound. Dynamic identifiers in `rows.ts` originate from static repository callers; no current request-to-SQL-injection path was established. Migrations execute trusted repository SQL. Do not weaken parameterization while implementing fixes.
- Path traversal through API page IDs/raw hashes was not established: IDs/hashes are validated before becoming filesystem paths. Same-user filesystem tampering is a distinct trust boundary.
- React renders source text as text; no `dangerouslySetInnerHTML` sink was found. Prompt injection in text returned to an external agent remains relevant, without implying browser XSS.
- Brain row validation is disabled in production (`packages/brain/src/store/rows.ts:5`), while SQL constraints cover only part of the domain schema. This amplifies the import/provenance boundary issues above; do not mistake TypeScript types or dev-only reads for external-input validation.
- JWT signature/fact/person/action validation, four-eyes approval, notifier ACL enforcement, HTTP/SSE session security and CI secret scanning cannot be verified because their services/workflows are absent. They are requirements in the threat model, not fabricated findings against nonexistent handlers.
- Existing tests cover visible-to listings, token consume/expiry, UPDATE/DELETE audit protection, corpus separation and prompt/schema helpers. They do not establish end-to-end caller authorization, immutable token state after an upsert, TRUNCATE protection, or grounded composition.
- No real secrets were intentionally read or printed. No current dependency advisories were checked. Run the separately planned Aikido review near delivery; this document is not that scan.

## Suggested remediation order (not implemented)

1. F01/F02: establish real caller identity and source/derived-result authorization before connecting real HR data or exposing services.
2. F04/F08/F10/F11/F12: protect mutations, token lifecycle, audit and operational targets.
3. F03/F09/F13/F14/F15/F16: bind provenance and enforce semantic/ACL boundaries before wiring the Brain pipeline.
4. F05/F06/F07/F17/F18: minimize retained data, bound work and align transport/error/deployment behavior with its documented contract.
